## 1. 触发一次评审

**⚠️ 真实写 GitHub**（如果走到回写步骤）。真实场景下由 GitHub webhook 自动触发，这里给的是
手动模拟 webhook 的方式，用于本地验证或排查。

```bash
REPO="<owner>/<repo>"
PR=<pr 号>
HEAD_SHA=<完整 40 位 head sha>
BASE_SHA=<完整 40 位 base sha>

BODY="{\"action\":\"opened\",\"repository\":{\"full_name\":\"${REPO}\"},\"pull_request\":{\"number\":${PR},\"head\":{\"sha\":\"${HEAD_SHA}\"},\"base\":{\"sha\":\"${BASE_SHA}\"}}}"
SIG="sha256=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac "$GITHUB_WEBHOOK_SECRET" | awk '{print $2}')"

curl -s -X POST http://127.0.0.1:8081/webhook/github -H "Content-Type: application/json" \
  -H "X-GitHub-Event: pull_request" -H "X-GitHub-Delivery: $(date +%s)" \
  -H "X-Hub-Signature-256: $SIG" -d "$BODY"
```

- `action` 取 `opened`（新 PR）或 `synchronize`（已有 PR 的新 push，走增量评审，见第 5 节）
- 成功返回 `{"code":0,"message":"ok","data":"ACCEPTED","success":true}`
- 同一个 `(repo, pr_number, head_sha)` 重放不会重复建任务（返回 `DUPLICATE`）

评审任务状态流转：`CREATED → PLANNING → REVIEWING → AGGREGATING → PUBLISHED`。
从 `AGGREGATING` 到 `PUBLISHED` 还要经过 outbox → MQ → integration 回写 GitHub，真实环境下
这一段通常要再等几十秒到几分钟（outbox dispatcher 默认 30s 一轮扫描）。查状态见第 7 节。

**一次评审实际做了什么**（4 维度并行 + 跨文件归约）：
1. `BUILD_CHANGE_MAP`：读整个 PR 的文件列表 + 签名变更，产出全局变更地图（不读 diff 本体）
2. `PLAN_CHUNKS`：按 AST 方法边界 + token 预算切片
3. `RECALL_RULES`：按 chunk 召回已上传的团队规范文档（见第 2 节），4 个维度共享结果
4. `REVIEW_CHUNK` × 4 维度（STYLE/SECURITY/PERFORMANCE/TEST）：并行跑真实 LLM 评审
5. `CHUNK_REDUCE`：按 fingerprint 去重同一 chunk 内多维度命中同一问题的情况
6. `GLOBAL_REDUCE`：只读各片摘要（不读原始 diff），发现跨文件的签名不一致等问题
7. 过滤：`FindingFilter` 召回否决记忆，判定是否跟开发者已经 👎 过的意见同类（见第 3、4 节）
8. 回写：生成行级评论（命中具体行号）+ 总结报告（命中不到具体行的意见），发布到 PR

## 2. 上传 / 更新团队规范文档

**只读/本地**（不涉及外部写入，rule-service 自己的接口）。

```bash
curl -s -X POST http://127.0.0.1:8084/internal/rules/documents \
  -H "Content-Type: application/json" \
  --data-binary @payload.json
```

`payload.json` 内容：
```json
{"project": "<owner>/<repo>", "title": "文档标题", "content": "Markdown 正文"}
```

**中文内容注意**：如果用 Git Bash + mingw 原生 `curl.exe`，不要用 `-d "$变量"` 或
`--data-raw` 直接传中文字符串，会把 UTF-8 字节搞坏导致服务端报「请求体无法解析」。
先把 JSON 写成文件再用 `--data-binary @file` 读，参考
[docs/demo/03-upload-rule.sh](demo/03-upload-rule.sh) 的写法（用 `node -e` 生成 payload 文件）。

返回示例：
```json
{"code":0,"message":"ok","data":{"document":{"id":93,"project":"...","title":"...","status":"ACTIVE","version":1,"uploadedAt":"...","chunkCount":1}},"success":true}
```

**版本替换规则**：同一 `(project, title)` 再次上传，旧版本自动转 `ARCHIVED`，新版本生效为
`ACTIVE`，召回只命中 `ACTIVE` 版本。

**文档切块规则**：按 Markdown 标题层级切（`#`/`##`/`###` 等），评审 prompt 里引用条款时用
`《文档标题》sectionPath` 的形式（比如 `《示例团队规范》3.2.1`）。

手动测试召回（不经过完整评审流程，直接调召回接口看结果）：
```bash
curl -s -X POST http://127.0.0.1:8084/internal/rules/recall \
  -H "Content-Type: application/json" \
  -d '{"project":"<owner>/<repo>","query":"方法命名规范","topK":5}'
```

## 3. 手动触发反馈轮询

**⚠️ 真实写 GitHub（读）**。真实场景下有定时器自动轮询（`CODEMIND_FEEDBACK_POLL_ENABLED`
默认开，间隔见 `codemind.feedback.lookback` 配置，默认回溯 14 天）。这里是手动触发，不等
定时器。

前置条件：开发者已经在 CodeMind 发的某条评论下**回复**了否决理由，并对该评论点了 👎
（thumbs down reaction）。两者都要有写权限的账号才算数（匿名/无权限账号的反馈不会被学习）。

```bash
curl -s -X POST "http://127.0.0.1:8081/internal/feedback/poll?repo=<owner>/<repo>&prNumber=<pr号>"
```

返回：
```json
{"code":0,"message":"ok","data":{"registered":1,"dispatched":1},"success":true}
```

- `registered`：本轮新识别到的反馈条数（回复 + 👎 的组合）
- `dispatched`：投递到 memory-service 学习队列的条数

**学习规则**（重要，决定反馈会不会被正确学到）：
- 同一个人既回复又 👎 同一条评论，只学回复内容（不会把 👎 单独当否决学一次方向错的）
- 多条评论合并评论里只有 👎、没有回复，记为 `AMBIGUOUS`，不学
- 学到的记忆内容形如 `[维度] 本项目允许/不要求……`，方向是「否决」，不是「要求」
- 重复轮询同一个 `(repo, pr)` 不会重复学习（`registered` 会变 0）

学习是异步的（走 MQ + LLM 抽取 + 冲突消解），轮询调用返回后还要再等 10~30s 才能在 memory
里查到，不是同步生效。

## 4. 查记忆（召回否决规则）

**只读/本地**。验证反馈有没有被正确学到，或者排查"为什么这条意见又出现了/为什么这条意见被
过滤掉了"时用。

```bash
curl -s -X POST http://127.0.0.1:8083/internal/memories/recall \
  -H "Content-Type: application/json" \
  --data-binary @payload.json
```

`payload.json`：
```json
{"project": "<owner>/<repo>", "query": "<关键词>", "kind": "REJECTED_PATTERN", "topK": 5, "minScore": 0}
```

- `kind` 可选：`REJECTED_PATTERN`（否决规则，M9 用）/ `COMMON_DEFECT`（常见缺陷模式）
- `minScore` 建议显式传 0 或设阈值，默认不传会按 0 处理，低分无关记忆也会返回
- `query` 走混合检索（embedding 余弦 + pg_trgm 文本相似度取较大值），**embedding 是本地
  特征哈希**（只认字面重叠，不懂同义改写），所以 query 用词最好跟记忆内容或原始 Finding
  的措辞接近，否则可能召回不到

返回每条记忆带 `similarity`/`decay`/`score` 三个打分因子，`score` 排序。`decay` 是遗忘衰减
（半衰期默认 30 天，越久没被强化分越低）。

**人工写入一条记忆**（不经过反馈学习，直接插入，调试用）：
```bash
curl -s -X POST http://127.0.0.1:8083/internal/memories \
  -H "Content-Type: application/json" \
  -d '{"project":"<owner>/<repo>","kind":"REJECTED_PATTERN","content":"[SECURITY] 本项目不要求对内部来源的参数做 null 校验","importance":0.9}'
```
同内容再写一次 = 强化（importance 取大、刷新衰减起点，`ARCHIVED` 状态的记忆会复活）。

## 5. 增量评审（第二次 push）

**⚠️ 真实写 GitHub**。同一个 PR 第二次触发 webhook（`action=synchronize`），只评审这次新增
的 diff，不是重新评审整个 PR。

```bash
BODY="{\"action\":\"synchronize\",\"repository\":{\"full_name\":\"${REPO}\"},\"pull_request\":{\"number\":${PR},\"head\":{\"sha\":\"${NEW_HEAD_SHA}\"},\"base\":{\"sha\":\"${BASE_SHA}\"}}}"
SIG="sha256=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac "$GITHUB_WEBHOOK_SECRET" | awk '{print $2}')"
curl -s -X POST http://127.0.0.1:8081/webhook/github -H "Content-Type: application/json" \
  -H "X-GitHub-Event: pull_request" -H "X-GitHub-Delivery: $(date +%s)" \
  -H "X-Hub-Signature-256: $SIG" -d "$BODY"
```

**走增量还是全量的判定逻辑**（`ReviewExecutionService.resolveDiff`）：
| 条件 | 结果 |
|---|---|
| 无历史评审基准 | 全量 |
| base 分支变了（rebase 过） | 全量 |
| GitHub compare API 返回非 `ahead`（比如强推、分叉） | 全量 |
| compare API 调用本身失败 | 全量（降级） |
| 有基准 + base 相同 + compare 返回 `ahead` | **增量** |

查上一次评审基准：
```bash
docker exec codemind-postgres psql -U codemind -d codemind -c \
  "select repo, pr_number, base_sha, head_sha from last_reviewed_head where repo='<owner>/<repo>' and pr_number=<pr号>;"
```

**跟反馈学习的联动**：如果之前对某类意见 👎 过（见第 3 节），增量评审里即使新 diff 又出现
类似代码，也不会再被评论（`FindingFilter` 在 Finding 产出后、报告生成前拦截，召回否决记忆
判同类）。

## 6. 查可观测指标

**只读/本地**。两个 Grafana 面板，也可以直连 Prometheus 数据源查。

```bash
curl -s -u admin:codemind http://127.0.0.1:3000/api/datasources   # 查数据源 uid
curl -s -u admin:codemind \
  --data-urlencode 'query=sum by (call_site) (codemind_llm_tokens_total)' \
  "http://127.0.0.1:3000/api/datasources/proxy/uid/<uid>/api/v1/query"
```

| 指标 | PromQL | 口径 |
|---|---|---|
| Token 用量（按调用场景） | `sum by (call_site) (codemind_llm_tokens_total)` | 累计计数器，任意时刻查都有效，不受时间窗口影响 |
| DAG 节点耗时 P95（按节点类型） | `histogram_quantile(0.95, sum by (le, node_type) (rate(codemind_dag_node_duration_seconds_bucket[5m])))` | **滑动窗口查询，查询时机是关键，见下方提醒** |

`call_site` 固定 7 个值：`STYLE`/`SECURITY`/`PERFORMANCE`/`TEST`/`CHANGE_MAP`/
`GLOBAL_REDUCE`/`FINDING_FILTER`。`node_type` 固定 6 个值：`REVIEW_CHUNK`/
`BUILD_CHANGE_MAP`/`CHUNK_REDUCE`/`GLOBAL_REDUCE`/`RECALL_RULES`/`PLAN_CHUNKS`。

**⚠️ P95 查询时机陷阱（2026-10-24 实测反复踩过，务必注意）**：DAG 节点耗时打点发生在任务
到达 `AGGREGATING` 之前（`GLOBAL_REDUCE` 在 `AGGREGATING` 阶段内完成），但任务要到
`PUBLISHED`（outbox 重投 + 回写 GitHub）通常还要再等 5~8 分钟。**如果等任务 `PUBLISHED`
之后才去查 P95，几乎必然滑出 5 分钟窗口拿到 NaN**——这不是配置错误。正确做法：盯着
`review.log` 看到 `状态 → AGGREGATING` 或 `跨会话评审完成` 这两行任意一行出现后，立刻查，
不等整个任务走完。

Prometheus 本身的 scrape interval 是 15s，`rate()` 至少要跨两个采样点才有意义——如果一次
评审产生的指标变化恰好落在同一个抓取窗口内，第一次查也可能是 0（不是 NaN，是 0），再等
15~30s 重查即可。

## 7. 查评审任务状态 / 排查卡住

```bash
# 单个任务
docker exec codemind-postgres psql -U codemind -d codemind -c \
  "select task_id, status, created_at, updated_at from review_task where repo='<owner>/<repo>' and pr_number=<pr号> order by created_at desc limit 5;"

# outbox（review 侧待投递）
docker exec codemind-postgres psql -U codemind -d codemind -c \
  "select t.task_id, t.status, o.attempts, o.next_attempt_at, o.acknowledged_at, o.last_error
   from review_task t left join review_publication_outbox o using (task_id)
   where t.task_id = '<task_id>';"

# integration 侧发送账本
docker exec codemind-postgres psql -U codemind -d codemind -c \
  "select task_id, state, mode, review_id, last_error, updated_at
   from integration.review_publication where task_id = '<task_id>';"
```

**卡在 AGGREGATING 不到 PUBLISHED 的常见原因**（按排查优先级）：

1. **MQ topic 积压**：历史失败消息把新消息堵住。查
   `docker exec codemind-rmq-broker sh -c 'cd /home/rocketmq/rocketmq-5.3.1/bin && sh mqadmin consumerProgress -n rocketmq-namesrv:9876 -g codemind-integration-review-completed'`，
   `Diff` 列正常应在几十条以内，几千条就是积压。处理：
   ```bash
   docker exec codemind-rmq-broker sh -c 'cd /home/rocketmq/rocketmq-5.3.1/bin && \
     sh mqadmin resetOffsetByTime -n rocketmq-namesrv:9876 -g codemind-integration-review-completed -t codemind-review-completed -s now && \
     sh mqadmin resetOffsetByTime -n rocketmq-namesrv:9876 -g codemind-integration-review-completed -t "%RETRY%codemind-integration-review-completed" -s now'
   ```
   **注意**：这会跳过所有未消费的历史消息（包括可能还有效的），只在确认积压都是已失效的
   历史数据时才这样做。

2. **GitHub token 限流**：`GITHUB_TOKEN`（integration 用来读 diff / 回写评论的账号）配额
   5000 次/小时，短时间内反复触发评审会打满。查：
   ```bash
   curl -s -H "Authorization: Bearer $GITHUB_TOKEN" https://api.github.com/rate_limit
   ```
   `remaining=0` 就只能等 `reset` 时间（Unix 时间戳）。

3. **integration 没起/没连上**：查 `integration.log` 有没有收到对应 `taskId` 的
   `ReviewCompletedListener` 日志。

4. **其它明确拒绝**（401/403/404/422/429）：查 `last_error` 字段，422 通常是 token 用户
   和 PR 作者是同一个账号（GitHub 不允许自己评审自己的 PR）。

更完整的运维排查手册见 [docs/operations/M7b-publication.md](operations/M7b-publication.md)。

## 8. 人工删除 / 归档记忆

```bash
# 删除单条（物理删除，不可逆）
curl -s -X DELETE http://127.0.0.1:8083/internal/memories/<id>

# 归档某项目下衰减到阈值以下的记忆（importance * decay < 0.05 默认阈值）
curl -s -X POST "http://127.0.0.1:8083/internal/memories/archive?project=<owner>/<repo>"
```

归档不是删除，是状态改成 `ARCHIVED`，不参与召回，但同内容再写入时会复活。删除是真的从库里
物理删掉。

## 9. 常见环境坑

- **本机 `python`/`python3` 是 Windows Store 占位程序**，不是真解释器。脚本里需要跨语言
  处理（JSON 转义等）用 `node -e` 或 Java，不要默认 python 可用
- **mingw 原生 `curl.exe` 处理中文命令行参数会损坏 UTF-8 字节**。涉及中文内容的请求体，
  先写文件再用 `--data-binary @file`，不要用 `-d "$变量"` 或 `--data-raw` 直接传
- **GitHub fine-grained token 无法访问"协作者身份参与、非持有者拥有"的仓库**，即使已接受
  协作邀请（`role_name=write`）。要用 classic token（`repo` scope）
- **宿主机原生 PostgreSQL 服务会占 5432 端口**与容器冲突，征兆是「用户 codemind 密码认证
  失败」，需要 `net stop postgresql-x64-16`（Windows 服务名可能不同）
- **全量 `mvn verify` 会耗尽 PG 连接数**，测试 Hikari 池已压到 2，仍建议不要并行跑多个
  verify
- **`/internal/**` 端点全部无鉴权**，网关的 discovery locator 会把它们暴露出去。网关开给
  本机之外访问前必须先封掉这些端点（显式排除路由或加服务间鉴权），这是已知未修的安全缺口
