# M11 rule-service：规范文档 RAG Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan
> task-by-task（任务链式依赖，见下方任务清单说明）。Steps use checkbox (`- [ ]`) syntax for tracking
> within each task's own step breakdown when executed.

**Goal:** 让上传的规范文档在评审中被真实召回并引用（ROADMAP M11 验证点：上传规范文档后，评审意见能引用对应条款）。

**Architecture:** 新建 rule-service（独立落地，复用 M8 memory-service 的技术路径：本地特征哈希 embedding
+ pg_trgm 两路召回、独立 schema）。review-service 新增 `RecallRulesNode`（DAG 节点，按 chunk 粒度召回、
4 个评审维度共享结果），结果注入 `ReviewAgent` 的 prompt，引用形式为 `Finding.message` 文本内嵌
`《文档标题》sectionPath`。

**Tech Stack:** Spring Boot 3.5.16、PostgreSQL 16 + pgvector + pg_trgm、Flyway、OpenFeign（服务间调用）、
Spring AI（仅 review 侧既有的 LLM 调用，rule-service 本身不调 LLM）。

**Spec:** `docs/superpowers/specs/2026-10-24-m11-rule-upload-design.md`

## Global Constraints

- domain 层不依赖 Spring 和任何基础设施（项目 CLAUDE.md 既定约定）
- 密钥只经环境变量注入；本里程碑不新增密钥
- rule-service 与 review-service 两侧 DTO / Embedder 实现各自独立定义，不跨模块共享类（M8/M9b 既定原则）
- `/internal/*` 端点无鉴权，同 M7a/M8/M9a 既有技术债，不在本里程碑解决
- 向量召回不建 HNSW、pg_trgm 用 `similarity() > 0` 不建 GIN，按 `(project, status)` 过滤精确扫描（M8 D4/D8 既定技术路径）
- 测试分两类：`*Test`（surefire，纯逻辑）与 `*IT`（failsafe，依赖真实中间件），按此命名归类
- 真实 LLM IT 缺 `CODEMIND_LLM_API_KEY` 时必须显式判失败，不用 `assumeTrue` 静默跳过（M4~M10 既定口径，跳过的测试不算通过）

## Review Focus

- `RuleDocumentChunker` 对异常 Markdown（标题层级跳跳、文档末尾无换行、标题本身为空字符串如 `"# "`）的处理是否和 T3 测试断言一致，不会切出空 `sectionPath`
- `RecallRulesNode` 的降级策略是否真的"静默"——确认没有把 `RuleRecallException` 的降级信息错误地传播成 `ChunkSummary` 或 `AgentReview` 的 `degraded=true`（会被 S6 规格轴判定为违反 D10）
- `DagOrchestrator` 新增的 `RuleRecallPort` 构造参数是否影响了 M5~M10 现有测试的构造器调用（向后兼容性断裂会导致大量既有测试编译失败）
- 版本替换的事务边界：`archiveActiveByProjectAndTitle` 与新文档插入是否在同一事务内，中途失败是否会留下"新旧都 ACTIVE"或"新旧都 ARCHIVED"的脏状态
- 真实 LLM 验收 IT 断言是否够具体（只断言 message 包含 sectionPath 字符串，还是连带断言该 Finding 确实对应违规那一行），避免 M9a 式"方向性错误但测试仍通过"的教训重演

## 设计共识（S1，对应 spec 的分节决定）

| # | 问题 | 决定 | 理由 |
|---|---|---|---|
| D1 | 服务拆分 | rule-service 独立落地（不并入 memory、不做 rule→memory 检索代理），复用 M8 技术路径 | 职责边界清晰，ARCHITECTURE 3.1 已定好六个服务；检索转发会造成「规则知识域反向依赖记忆域」的语义错误 |
| D2 | 文档格式 | 仅 Markdown / 纯文本 | 解析零依赖；docx/PDF 留技术债 |
| D3 | 切块策略 | 按 Markdown 标题（`#`~`######`）层级切块，`sectionPath` 取标题文本按层级拼接；空块跳过 | 让"对应条款"有机器可判定、语义完整的引用单位；不强制要求文档写死编号 |
| D4 | 检索技术路径 | 本地特征哈希 embedding（`HashingEmbedder`，256 维，算法与 M8 一致但独立维护一份实现）+ pg_trgm；两路候选取 `max(余弦, pg_trgm)` 排序，不含 importance/decay | 与 M8 保持一致（中转端点无 embedding 模型）；规则条款没有"重要性/衰减"概念，只有 ACTIVE/ARCHIVED 两态 |
| D5 | review 接入点 | 新 DAG 节点 `RecallRulesNode`，按 chunk 粒度调用一次（4 个维度共享结果，不重复召回 4 次） | 对应 ARCHITECTURE 5 图中留的 RecallContext 节点；4 维度查询文本相同，重复调用纯浪费 |
| D6 | 引用形式 | `Finding.message` 文本内嵌 `《文档标题》sectionPath`，不新增结构化字段 | 改动面小，不动 `Finding` 值对象 / 解析器 / 数据库列 / 对外展示格式 |
| D7 | 文档更新 | 版本替换：同 `project+title` 重新上传时，旧文档整体转 `ARCHIVED`，新文档全 `ACTIVE`；召回只查 `ACTIVE` | 同 M8 memory 的 ACTIVE/ARCHIVED 思路，但没有"强化"语义（规则不是记忆） |
| D8 | 上传入口 | 仅 REST 接口，无前端/CLI | 跑得通就行，范围收紧 |
| D9 | 作用域 | 按 project 隔离（与 memory 一致） | 多项目场景不串规范 |
| D10 | 召回降级 | `RecallRulesNode` 召回失败 / 无候选 → 静默返回空列表，不计入 `degradations`；只记 debug 日志 | 规则缺失不代表评审质量下降（本来就可能没有匹配条款），与 `FindingFilter`「过滤失败必须放行且要可见」的严重级别不同 |
| D11 | 存储 | 独立 schema `rule`，Flyway `db/rule-migration`，同 integration/memory 做法 | 与其他服务迁移历史互不扫描 |
| D12 | 验收样例 | 1 个真实 LLM IT 固定资产样例：规则 + 违反该规则的 diff，断言 Finding.message 含 sectionPath；缺 key 显式判失败，不用 `assumeTrue` 静默跳过 | 与 M4~M10 既定口径一致：跳过的测试不算通过 |

## 接口（内部，无鉴权，同 M7a/M8/M9a 既有缺口）

- `POST /internal/rules/documents` `{project, title, content}` → 文档（含切块数）
- `POST /internal/rules/recall` `{project, query, topK?}` → 按 score 降序，每条带 `sectionPath / heading / content / similarity`

输入上限：`content` ≤ 50000 字符（整份文档）、`query` ≤ 8000（与 M8 一致）、`project` ≤ 255、`title` ≤ 255、
`topK` ∈ [1, 20]（规则候选远少于记忆，上限收紧）。参数非法统一 400 + `Result`。
