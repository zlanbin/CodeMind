# M10 增量评审

> 设计输入：ARCHITECTURE 5（DAG 图）、7.1（L1 任务记忆已发布指纹，M8 建好留给 M10）。
> 验证点（ROADMAP）：第二次 push 只评审新 diff，不重复发评论。
> 用户在判定门对 9 个未决点逐条拍板（2026-10-24），见 D1~D9。

## 现状（S0 探索确认）

- `review_task` 唯一索引 `(repo, pr_number, head_sha)`：同一 PR 第二次 push（新 head_sha）会建一条**全新任务**，
  DAG 把当前 head_sha 的**全量** diff（`base...head`，GitHub `pulls/{n}` 整份 diff）重新跑一遍，无任何「只看新增」逻辑
- M8 已建好 L1 已发布指纹基础设施但零调用方：`memory.task_fingerprint` 表、`TaskFingerprintService.record/published`、
  `POST|GET /internal/task-fingerprints`
- `Finding.fingerprint = hash(file + category + normalize(codeSnippet))`，M5/M9b 已复用，M10 第三次复用
- `ReviewPublicationService.markPublished` 在同一事务里 `findByIdForUpdate` 查出完整 `ReviewTask`
  （含 `repo/prNumber/headSha/baseSha/report()`），是本里程碑新增状态落点的天然挂钩

## 设计共识（S1）

| # | 问题 | 决定 | 来源 |
|---|---|---|---|
| D1 | 前一次已评审到哪 | 新建独立表 `review.last_reviewed_head`（`(repo, pr_number)` 主键），不复用 `review_task` 历史记录判定 | 用户：新建独立表 |
| D2 | 增量 diff 评审流程 | 增量 diff 跑完整条现有 M6 DAG（PlanChunks→4N 评审→ChunkReduce→GlobalReduce），不走简化路径 | 用户：最小改动 |
| D3 | 文件新侧全文取法 | 直接把 `fetchNewSources` 的 `ref` 换成 `new_head`，复用现有逻辑，不新增接口 | 用户：复用现有逻辑 |
| D4 | 增量结果要不要再去重 | 增量评审完成后仍过一道 M8 已建的 `task_fingerprint` 对比，不完全信任增量 diff 本身不产出重复意见 | 用户：要过指纹对比 |
| D5 | 首次评审 / rebase（base 变更）处理 | 两种场景都回退到现有全量 diff 流程（`base...head`），不走 compare API | 用户：回退全量 |
| D6 | `last_reviewed_head` 写入时机 | 回写成功后才写，不在任务创建/评审完成时写（避免把失败/卡住的任务当成基准，漏评已改未评的代码） | 用户：回写成功后 |

## 架构设计（S1 延伸，供 S2 制定方案时对齐）

### 取 diff 的决策树

在 `ReviewExecutionService.executeReview` 里，原来直接调 `scmContentPort.fetchDiff(repo, prNumber)` 之前：

1. 查 `last_reviewed_head`，没有记录 → 全量 diff（现状不变，首次评审场景）
2. 有记录但其 `base_sha` 与当前任务的 `base_sha` 不一致 → 全量 diff（rebase 场景，D5）
3. 否则 → 调 compare API；响应里的 `status` 非 `ahead`（如 `diverged`，D9）→ 全量 diff
4. 否则 → 增量：取 compare API 返回的 `old_head...new_head` diff 文本

文件新侧全文（`fetchNewSources`）**不受影响**：一直按 `task.headSha()` 取，增量/全量场景下都是 new_head 上的完整内容（D3）。

### 新增的跨服务端点

GitHub compare API 一次调用同时给 `status` 字段（JSON，`application/vnd.github+json`）和 diff 内容
（`DIFF_MEDIA_TYPE`），但不能用同一个请求同时拿两种格式——`GithubScmClient` 需要先用 JSON 媒体类型调一次拿
`status`，确认 `ahead` 才用 `DIFF_MEDIA_TYPE` 再调一次拿 diff 文本；或者只用 JSON 媒体类型一次性拿
`status` + 响应体里的 `files[].patch` 拼出 diff（更省一次网络调用，GitHub compare 的 JSON 响应本身带
每个文件的 patch 片段）。两种做法的取舍留给 S2 制定方案时定，本节只定端口契约：

- integration：`ScmClient.fetchCompareDiff(repo, oldHead, newHead)` → `CompareResult(String status, String diffText)`
  值对象，`status` 非 `ahead` 时 `diffText` 可为空；`GithubScmClient` 调 GitHub compare 接口实现；
  `PullRequestContentService.compareDiff` 转发；`PullRequestContentController` 新增
  `GET /internal/pulls/compare-diff?repo=&oldHead=&newHead=`，JSON 返回 `{status, diffText}`
  （不能像 `/diff` 端点一样纯文本返回，因为要带 `status` 字段）
- review：`ScmContentPort.fetchCompareDiff` 同签名返回对应的 `CompareResult`（review 侧自己的值对象，
  不跨模块共享类型，同 M9a/M9b 既有做法）+ `FeignScmContentAdapter` 实现 + `IntegrationScmFeignClient` 新方法

### 新表（review 侧 V6 迁移）

```sql
create table last_reviewed_head (
    repo        varchar(255) not null,
    pr_number   integer      not null,
    base_sha    varchar(64)  not null,
    head_sha    varchar(64)  not null,
    updated_at  timestamptz  not null default now(),
    primary key (repo, pr_number)
);

create table fingerprint_registration_outbox (
    task_id          uuid primary key references review_task(task_id),
    repo             varchar(255) not null,
    pr_number        integer      not null,
    fingerprints     jsonb        not null,
    created_at       timestamptz  not null default now(),
    next_attempt_at  timestamptz  not null default now(),
    lease_token      uuid,
    lease_until      timestamptz,
    attempts         integer      not null default 0 check (attempts >= 0),
    acknowledged_at  timestamptz,
    last_error       varchar(256),
    check ((lease_token is null) = (lease_until is null))
);
```

### 已发布指纹过滤 + 登记的落点

- **过滤**：在 `FindingFilter`（M9b）之后、`reportBuilder.build(...)` 之前新增一步，调
  `TaskFingerprintPort.published(repo, prNumber)`（新端口，Feign 调 memory 已有的 `GET /internal/task-fingerprints`，
  模式同 M9b 的 `MemoryRecallPort`）拿已发布指纹集合，命中的 Finding 滤掉。**失败就放行**，不因查询失败漏发真缺陷
  （同 `FindingFilter` 的降级原则），只记一条 degradation
- **登记时机**：不在评审完成当下登记（发布可能失败/降级，指纹不该标记为「用户已看到」）。落点在
  `ReviewPublicationService.markPublished` 确认推进到 `PUBLISHED`（非重复回执）的那笔事务里：
  1. 从 `task.report()`（`inline()` 的 `merged()` + `summary()` 的 `finding()`）收集最终进报告的全部 `Finding.fingerprint()`
  2. 事务内：`upsert last_reviewed_head`（本地操作，不涉及跨服务调用，可以在事务内）
  3. 事务内：把收集到的指纹列表落进 `fingerprint_registration_outbox`（`task_id` 主键天然幂等）
  4. 事务**外**：新增 `FingerprintRegistrationDispatcher`（镜像 `ReviewOutboxDispatcher` 的 SKIP LOCKED 认领 + 租约 +
     退避重试写法）定时扫账本，调 `TaskFingerprintPort.record(repo, prNumber, fingerprints)`，成功 `acknowledge`

**不能**把指纹登记的 Feign 调用放进 `markPublished` 的数据库事务内部：外部调用失败会导致事务回滚，把已经成功的
发布状态也一起回滚，这是错的（D8 的账本机制正是为了把「本地状态推进」和「跨服务登记」解耦，保证前者不被后者拖累）。

`FingerprintSchedulingConfig`（新文件，与现有 `PublicationSchedulingConfig` 并列同风格）装配 dispatcher + 定时任务。

## M10 实施计划（S2）

> **执行方式：** 本计划按 `superpowers:executing-plans`（单会话内顺序执行，任务间有接口依赖）实施，
> 每个任务配 `superpowers:test-driven-development`；测试失败走 `superpowers:systematic-debugging`。

**目标**：第二次 push 只评审新 diff（GitHub compare API 增量），已发布过的意见不重复出现在回写评论里。

**架构**：`ReviewExecutionService` 在取 diff 前查新表 `last_reviewed_head` 决定全量/增量（4 条回退判断：
无记录、base 变了、compare status 非 ahead、以上都不是才真正增量）；`FindingFilter`（M9b）之后插一道已发布
指纹过滤（查 M8 已建端点）；`ReviewPublicationService.markPublished` 确认发布成功后，同一事务内 upsert
`last_reviewed_head` + 落一条待登记指纹到新账本 `fingerprint_registration_outbox`；新 dispatcher 异步把账本
里的指纹登记到 memory（同步 HTTP 调用，成功即确认——不是 M7b 的 outbox+MQ+回执两阶段模式，因为这里的「发送」
本身就是最终写入、响应码就是成败判定，不存在「发了但不确定对方收到没」的不确定态）。

**Tech Stack**：复用现有 Spring Cloud OpenFeign（已在模块依赖里）；复用 `JdbcClient` + `TransactionTemplate`
（M7b outbox 已用的持久化风格）。

**Spec**：`docs/plans/M10.md` 本文件前半部分（D1~D9、架构设计、改动范围）；`docs/ARCHITECTURE.md` 5（DAG 图）、
7.1（L1 已发布指纹）；`docs/ROADMAP.md` M10 验证点。

### Global Constraints

- 所有新 Feign 客户端调 memory 的 internal 端点，返回类型必须声明为 `Result<T>` 并在适配器里取 `.data()`——
  **M9b 的 Critical 发现**：memory 的 internal 端点统一套 `Result` 信封，裸 DTO 会让 Feign 解码后业务字段恒为
  `null`。新增的 `TaskFingerprintFeignClient` 不能重复这个错误
- D5/D9 的回退判断（首次评审、base 变更、compare status 非 ahead）统一走现有的全量 diff 路径，
  不单独写一套"半增量"逻辑——出现任何不确定场景就退回已验证过的旧路径
- 指纹过滤/登记失败一律按"失败就放行/不阻塞主流程"降级，不让 memory 不可用拖垮评审主链路
  （同 `FindingFilter` 的既有原则）
- 不把跨服务 HTTP 调用放进数据库事务内部（`markPublished` 的本地状态推进与指纹登记的跨服务调用必须解耦，
  同 M7b outbox 的既有原因：外部调用失败不能回滚已经成功的本地状态）

### Review Focus

- GitHub compare API 返回 `status=behind`（本地 head 实际落后于 base，异常场景）或 `diverged` 时必须回退全量 diff，
  不能把这类响应误当 `ahead` 处理导致拿到错误方向的 diff
- `last_reviewed_head` 表在同一个 `(repo, pr_number)` 反复 upsert 时必须覆盖旧值而不是报错或插重复行
  （PK 冲突时的 upsert 语义要测到）
- 指纹登记账本 `fingerprint_registration_outbox` 的 `task_id` 主键天然幂等，但要测到「同一个 task 的回执被
  消费两次（MQ at-least-once）不会导致指纹被登记两次、也不会在插入时报唯一约束错误中断主流程」
- 已发布指纹过滤与 M9b 的 `FindingFilter`（否决记忆过滤）是两道独立的过滤步骤，必须验证顺序和叠加效果：
  一条 Finding 既不是否决同类、又命中已发布指纹，应该被第二道过滤拦住，不能因为通过了第一道就被误认为会进报告
- 增量 diff 为空（比如这次 push 只改了非 Java 文件、或者是 merge commit 没引入新代码变化）时，
  DAG 的空 diff 早退路径（`diffText.isBlank()`）要仍然适用，不能因为走的是 compare 分支就绕过这条已有逻辑

public class FingerprintRegistrationDispatcher {
    public int dispatchDue() {
        var deliveries = outbox.claimDue(clock.instant(), batchSize, lease);
        deliveries.forEach(this::send);
        return deliveries.size();
    }

    private void send(FingerprintRegistrationDelivery delivery) {
        var reg = delivery.registration();
        try {
            taskFingerprintPort.record(reg.repo(), reg.prNumber(), reg.fingerprints());
            outbox.acknowledge(reg.taskId(), clock.instant());
        } catch (TaskFingerprintException e) {
            log.warn("指纹登记失败 taskId={} error={}", reg.taskId(), e.getMessage());
            outbox.reschedule(reg.taskId(), delivery.leaseToken(), clock.instant().plus(retryDelay),
                    e.getClass().getSimpleName());
        }
    }
}
