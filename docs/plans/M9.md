# M9 反馈闭环与冲突消解

> 设计输入：ARCHITECTURE 7.2。验证点（ROADMAP）：对某条意见 👎 后再提同类代码，该意见不再出现。
> 用户在判定门对 5 个未决点逐条拍板（2026-10-23），见 D1~D5；其余细节按下表取默认值。

## 拆分

范围跨 integration / memory / review 三个服务，一个会话做不完，按 ROADMAP「里程碑过大时」拆：

| 子项 | 内容 | 独立验证点 |
|---|---|---|
| **M9a** 反馈进来 | 行级评论带指纹标记、integration 轮询 👎 / 回复 → `FindingFeedbackReceived` → memory LLM 抽取 + ADD/UPDATE/DELETE 消解 | 对真实 PR 上一条 CodeMind 行级评论 👎 后，memory 里出现对应的 `REJECTED_PATTERN` 记忆；重复轮询不重复学习 |
| **M9b** 过滤生效 | review 的 Dedup & Filter（召回否决记忆 + LLM 判定同类）+ 真实端到端验收 | ROADMAP M9 原验证点 |

## 设计共识（S1）

| # | 问题 | 决定 | 来源 |
|---|---|---|---|
| D1 | 反馈怎么拿到 | integration 定时轮询已发布 review 的行级评论的 👎 reaction 与人工回复；另加手动触发端点 | 用户：可以（GitHub 无 reaction webhook，本机 8081 外网不可达） |
| D2 | 评论怎么对回 Finding | `renderInline` 对每条合并进来的 Finding 追加隐藏标记 `<!-- codemind:finding fp=<fingerprint> cat=<CATEGORY> -->`；格式与解析放 `codemind-common` 的 `FindingMarker`（写方 review、读方 integration 共用契约）。M9 之前发布的评论无标记、收不到反馈 | 用户：可以 |
| D3 | 怎么判同类 | 召回否决记忆做候选，再由 LLM 判定 Finding 是否属于被否决的同类（A 方案，M9b） | 用户：A |
| D4 | 抽取与消解 | 都走 LLM，stub 测试确定性、真实 LLM IT 宽松检查；LLM 失败降级为模板 ADD | 用户：可以 |
| D5 | 验收 | sandbox 仓库：先发一份带标记的 review → 👎 → 轮询学习 → `lan-bin` 开同类代码新 PR → 意见不再出现。每次真实写前停下确认 | 用户：可以 |
| D6 | 哪些算反馈 | 👎（`-1` reaction）算否决，但受 D15 / D16 约束；对 CodeMind 评论的**回复**都转发，由 memory 的 LLM 判断是不是否决（「谢谢已改」这种不学）。作者须过 D13 | 默认，T6 后修订 |
| D7 | 轮询范围 | 账本里 `PUBLISHED` 且 `updated_at` 在最近 14 天内的 review；只看 `pull_request_review_id` 等于账本 `review_id` 的评论 | 默认 |
| D8 | 反馈去重与可靠投递 | integration 新表 `integration.finding_feedback`，唯一键 `(repo, source_type, source_id)`（source_id = reaction id 或回复评论 id）；状态 `PENDING → SENT`，登记与发送分离，后台重投 PENDING（同 M7b outbox 思路，但单服务内） | 默认 |
| D9 | 事件内容 | `FindingFeedbackReceived(eventId, occurredAt, repo, prNumber, commentId, feedbackType, sourceId, author, replyText, commentBody, findings[fingerprint, category])`，`commentBody` 已剥掉标记 | 默认 |
| D10 | memory 侧幂等 | `memory.feedback_event(event_id pk)` 记已处理的事件与决定；LLM 不确定，重放不能再学一遍 | 默认 |
| D11 | 消解语义 | 召回同 project 最相关的 5 条记忆（任意 kind，score ≥ 0.05）交给 LLM：`ADD` 新增；`UPDATE id` 改写（删旧 + 写新，同事务，正文强制保留新规则的 `[维度]` 前缀）；`DELETE id` 删掉矛盾记忆后 ADD；`NOOP id` 只强化。**约束（S6）**：NOOP / UPDATE 只能落在 REJECTED_PATTERN，DELETE 不能删 CONVENTION，违反或指向候选外一律退回 ADD——保证结果里总有一条否决记忆。importance：👎 0.8、带理由的回复 0.9 | 默认 |
| D13 | 谁的反馈算数 | 只学对仓库有写权限的账号（`collaborators/{login}/permission` 为 admin/maintain/write），另可配白名单 `codemind.feedback.trusted-logins`；查不到权限按不可信 | S6 标准轴：公开仓库外人 👎 可压掉真缺陷 |
| D15 | 同一人既 👎 又回复 | 只学回复；👎 在 integration 账本登记为 `SUPERSEDED`（占位去重、永不投递）。integration 先处理回复再处理 👎 | 用户（T6 实测后） |
| D16 | 合并评论只有 👎 | 评论含 >1 条不同指纹的 Finding 且只有 👎：memory 记 `AMBIGUOUS`、不调 LLM、不学。单条 Finding 的评论照常学 | 用户（T6 实测后） |
| D17 | 抽取方向 | prompt 要求规则写成「本项目允许 / 不要求……」并给正反例；👎 时直接告诉模型「已确定是否决」 | 用户（T6 实测后） |
| D14 | 坏数据与重投上限 | 账本加 `FAILED`：payload 反序列化失败就地转 FAILED；投递失败 10 次转 FAILED。memory 侧事件先占位再写记忆（并发重投后到者立刻回滚）；模板降级学到的 outcome 带 `DEGRADED:` 前缀 | S6 两轴 |
| D12 | memory 接 LLM | 新增 domain 端口 `LlmClient` + Spring AI 适配器（与 review 各自一份，不跨模块共享）；同一中转端点与 key | 默认 |

### S6 评审与处理（M9a，固定点 `3a26ee0`，两轴独立子代理）

标准轴 0 硬违规；规格轴 1 严重（NOOP 落在 COMMON_DEFECT 上会强化被否决缺陷且不留否决记忆）。回 S5 已修：
D11 约束与前缀、编造维度整条丢弃、D13 反馈人鉴权、D14 坏数据 / 重投上限 / 先占位、定时器两步分开兜底、
`ClockConfig` 单列、`on conflict` 写明目标、handler 补日志。已知限制（记入 PROGRESS）：撤销 👎 不回收记忆；
memory 消费重试耗尽进死信后反馈丢失（integration 已标 SENT）；模板降级无自动补学；合并评论被 👎 时每个维度各学一条；
SUMMARY_ONLY 降级发布的评论收不到反馈；N+1 调 GitHub、匿名限流无退避；NOOP 期间目标被并发删除会被写回。

T6 必须证明（规格轴列出）：GitHub 返回的评论正文保留标记；`pull_request_review_id` = 账本 `review_id`；
`content=-1` 过滤可用；线上 integration 的事件被 memory 消费，`feedback_event.outcome` 为 `ADD#…`（**不带 `DEGRADED:`**），
对应行是带 `[维度]` 前缀的 REJECTED_PATTERN；再轮询 `registered=0`、记忆不增；必须带真实 LLM key。
