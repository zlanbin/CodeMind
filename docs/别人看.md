# CodeMind 智能代码评审平台

> 面向技术面试官/团队成员的系统介绍：它是什么、为什么这样设计、能帮你做什么。

## 一句话

PR 提交后自动触发多 Agent 并行评审，按代码规范、安全、性能、测试四个维度给出行级评论。
系统记住团队规范和开发者否决过的意见，越用越准。

## 它能帮你做什么（场景介绍）

### 1. 提 PR 自动收到行级评审意见

GitHub webhook 触发后，系统在后台跑完整评审流程，几十秒到几分钟内把意见直接发布到 PR——
总结性意见放在评审总述，能定位到具体行的意见直接挂在那一行上，点开就能看到问题描述、
严重程度、维度分类（代码规范/安全/性能/测试）和修改建议。开发者不需要主动做任何事，提交
代码就有评审在等着。

### 2. 团队规范可以配置，意见会引用具体条款

把团队的编码规范文档（Markdown 格式）上传给系统，之后评审意见命中规范条款时会直接引用
「《团队规范》3.2.1」这样的具体章节，而不是泛泛地说"建议遵循规范"。规范更新后重新上传，
旧版本自动失效，新版本立刻生效，不需要重新部署或重启任何服务。

### 3. 对误判的意见可以表达"不认同"，系统会记住

如果某条评审意见不适用于你的项目（比如"内部工具类的参数不需要做 null 校验"这种团队内部
已达成一致的例外），在评论下回复理由并点 👎，系统会用 LLM 把你的理由抽取成一条规则，
存进项目的长期记忆。下次遇到同类代码，这条意见不会再出现——但真正的缺陷（比如一个新的、
性质不同的 bug）不会被这条规则误杀，因为过滤器是按语义相似度判断"是不是同一类意见"，
不是简单的关键词匹配或者全局静音。

### 4. 同一个 PR 反复 push，只审新增的部分

开发中反复推送新 commit 是常态，系统不会每次都把整个 PR 从头审一遍——只评审这次新增的
diff，已经评审过的部分不重复发评论，已经被你否决过的意见类型也不会在新代码里死灰复燃。

### 5. 系统本身的运行状况可以实时看到

每次 LLM 调用消耗了多少 token（按触发场景分类统计）、评审流程里每个环节耗时多少（P95
延迟），都能在 Grafana 面板里实时查到，不是黑盒跑完就什么都不知道。

## 它是怎么设计的（技术介绍）

### 整体架构

6 个微服务，DDD 四层分层（interfaces/application/domain/infrastructure），domain 层不依赖
任何 Spring 或基础设施，纯 Java：

| 服务 | 职责 |
|---|---|
| gateway | 按服务名路由，Spring Cloud Gateway |
| integration | 唯一直连 GitHub 的服务：webhook 接入、拉 diff/文件内容、回写评论、轮询反馈 |
| review | 核心编排域：自研 DAG 引擎、多 Agent 并行评审、跨会话归约 |
| memory | 分层记忆：写入/混合检索/衰减/反馈学习闭环 |
| rule | 团队规范文档的切块、embedding、召回（RAG） |
| admin | 报表域（当前最简化） |

通信上，服务间同步调用走 OpenFeign，领域事件走 RocketMQ 异步传递（比如评审完成事件、反馈
收到事件）。存储用 PostgreSQL + pgvector（关系数据和向量数据同库），Redis 做幂等与锁。

**只有 integration 直连 GitHub**——review 不感知具体 SCM 平台，想接 GitLab 只需要换
integration 侧的适配器实现。token 也只集中在一个服务里管理，缩小了密钥暴露面。

### 核心设计一：自研 DAG 引擎 + 多 Agent 并行

评审流程本质是一个"解析 → 并行多 Agent → 聚合"的有向无环图。自己写了一个精简版 DAG 调度
引擎（不是用现成的工作流框架），支持：

- 虚拟线程并行执行同一层级的节点
- 动态扇出：切片数量运行时才知道，调度器据此动态产出下游子图（1 个 chunk 对应 4 个维度的
  评审节点，N 个 chunk 就是 4N 个并行评审）
- Checkpoint 续跑：每个节点执行完结果落库，进程中途挂掉重启后已完成的节点不重复跑（也就
  不重复消耗 LLM 调用）
- 超时 + 重试：单节点级别可配置

四个评审维度（代码规范/安全/性能/测试）各自是独立的 Agent，并行调用 LLM，输出的 Finding
按内容特征计算 fingerprint（文件+分类+代码片段归一化后哈希），同一个问题被多个维度同时
命中时只保留严重程度最高的一条，不会在 PR 上看到重复意见。

### 核心设计二：跨会话 Map-Reduce（应对大 PR 超出上下文窗口的问题）

这是整个系统设计上最花心思的部分。大 PR（比如 40 个文件、3000 行改动）如果把全部 diff 一次
性塞进一次 LLM 调用，会超出上下文窗口；即使硬塞得进去，长上下文下的评审质量也会明显下降
（LLM 在超长输入里容易"看不清"局部细节）。

解决思路是分层 Map-Reduce：

1. **全局变更地图**（1 次轻量 LLM 调用）：只输入文件列表、方法签名变更、增删行数统计，
   不输入 diff 本体，输出 PR 的整体意图、模块划分、高风险文件。方法签名变更由 AST 解析 +
   diff 删除行模式匹配**确定性**提取，不依赖 LLM 判断——这保证了即使 LLM 这一步整体失败，
   签名变更信息依然完整可用（它是后续跨文件问题检测的关键依据）
2. **语义切片**（纯算法，不调 LLM）：diff 按 AST 方法边界切（不会把一个方法的改动切成两半），
   有调用关系的改动尽量合并到同一个切片里，再按 token 预算贪心装箱。如果合并后的聚合体
   超出预算，会沿着"调用关系合并"的缝隙拆开（但绝不拆开一个完整方法——这是硬约束，排在
   预算考虑之前）
3. **子会话并行评审**（N 个并行 LLM 调用）：每个切片独立评审，除了产出 Finding，还要产出
   一份结构化摘要（改动的符号、风险点、"我看不到但可能影响我的跨片问题"）
4. **全局归约**（1 次 LLM 调用）：只读第 1 步的变更地图和第 3 步各切片的摘要，**完全不碰
   原始 diff**，专门用来发现"调用方在这个切片，定义方在另一个切片，两边签名不匹配"这类
   单个切片内发现不了的跨文件问题

验证这个设计有没有真正起作用的方式很直接：构造一个 4 文件的 PR，让调用方和定义方被切到
不同的切片里（确保任何单个切片内都看不到完整的调用链），断言只有全局归约这一步能发现签名
不匹配——如果全局归约被跳过或者输入错误，这个问题就应该被漏掉，用这个"反证"来证明 Map
阶段确实把足够的信息传递到了 Reduce 阶段，不是摆设。

### 核心设计三：分层记忆 + 反馈学习闭环

记忆分四层：L0 单次 LLM 调用内的工作记忆，L1 单个 PR 生命周期内的任务记忆（已发布意见的
指纹，用于增量评审去重），L2 项目级长期记忆（团队规范、被否决的意见模式，带时间衰减），
L3 开发者画像（当前最简化）。

反馈闭环的完整链路：开发者在某条评审意见下回复理由并点 👎 → GitHub 没有 reaction 的
webhook，所以 integration 定时轮询 PR 评论和 reaction → 识别出"回复 + 👎"的组合 → 可靠
投递到 memory-service（账本表保证至少一次投递，去重用事件 ID）→ LLM 把反馈内容抽取成
"本项目允许/不要求……"这种明确否决方向的规则 → 和已有记忆做冲突消解（新增/更新/删除/
无操作，有硬约束防止误删真缺陷类记忆）→ 下次评审时，新产出的 Finding 在正式发布前会先
召回同项目的否决记忆，用 LLM 判断是否属于同一类意见，命中就过滤掉不发布。

这里有两个容易踩的坑，设计时特别处理过：

- **方向一致性**：抽取时必须明确"这是否决规则"而不是误抽取成"这是要求规则"（原意见说
  "缺少 null 校验"，开发者否决后应该学成"本项目不要求 null 校验"，不能学反成"本项目要求
  null 校验"——早期版本真的翻车过一次，方向学反了会把真缺陷连带过滤掉）
- **误杀风险**：过滤判断走的是"召回候选 + LLM 语义判定"两步，不是关键词匹配，也不是
  "一旦否决某类意见就全局静音该分类"——否则团队否决了一次"不需要加 null 校验"的意见后，
  未来真实存在的 NPE 风险也会被一刀切过滤掉。过滤器设计上要求召回到具体候选记忆并且 LLM
  判定确实语义相近才拦截，召回失败或 LLM 判断失败都默认放行（宁可多发一条意见，不能漏掉
  真缺陷）

Embedding 目前用的是本地特征哈希（字符 bigram + 词特征哈希），不是真实的语义向量模型，
因为可用的 LLM 中转端点不提供 embedding 模型。这意味着当前的语义召回只能识别字面上有
重叠的内容，不能理解同义改写——这是已知的能力边界，不是设计缺陷，换成真实 embedding 模型
只需要替换一个适配器实现。

### 其它值得一提的技术决策

- **增量评审**：PR 第二次 push 时，用 GitHub compare API 判断能否走增量 diff（base 分支
  没变、compare 返回明确的 ahead 关系才走增量，否则安全回退到全量），只对新增的 diff 重新
  跑一遍完整的 DAG 流程，已发布过的 Finding 按 fingerprint 过滤不重复发
- **可靠的回写机制**：评审完成到真正发布到 GitHub 之间用 outbox 模式 + 消息队列解耦，结果
  不确定时（网络超时、进程中途退出）不会盲目重发——先查 GitHub 上是否已经发布过（通过
  隐藏的 HTML 注释标记识别），确认没有才重发，避免同一个评审在 PR 上出现两次
- **可观测性**：Token 消耗按调用场景（评审维度/全局归约/反馈过滤等）分类打点，DAG 各类型
  节点的执行耗时用直方图统计（支持 P95/P99 等分位数查询），接入 Prometheus + Grafana

### 技术栈

Spring Boot 3.5 + Spring Cloud + Spring Cloud Alibaba（Nacos 服务发现），Spring AI 接 LLM
（OpenAI 兼容协议），PostgreSQL 16 + pgvector 做向量检索，RocketMQ 做事件总线，Redis 做
幂等和分布式锁，JavaParser 做 AST 解析，jtokkit 做真实 BPE token 计数（不是字符数估算），
Micrometer + Prometheus + Grafana 做可观测。

### 当前已知的能力边界

- 只支持 Java 的 AST 语义切片，其他语言降级为按 diff hunk 切片（粒度更粗）
- 只支持 GitHub，GitLab 等其他平台的接口层已预留但未实现
- Embedding 是本地特征哈希，不是真实语义模型（见上）
- 所有服务间 internal 端点目前无鉴权，只适合部署在不对外暴露的内部网络
- 不做自动修复 PR、不做多租户计费、不做模型训练
